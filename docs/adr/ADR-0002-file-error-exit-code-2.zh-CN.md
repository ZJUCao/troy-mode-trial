# ADR-0002：`wordcount` 遇到文件错误时以退出码 2 退出

## 1. 状态

已接受（Accepted）

## 2. 背景

ADR-0001 决定的第 4 点和架构 2.0 第 6 节规定，cli 遇到文件错误时返回退出码 1：文件不存在、无权读取文件，或文件不是有效的 UTF-8。F04 原型显示文件不存在时 `$LASTEXITCODE` 为 1。命令行写错时按 `argparse` 的做法以退出码 2 退出，未捕获的异常经 Python 的 traceback 以退出码 1 退出。

Troy 在 F04 接口设计的 PR #39 上评论：“when the file is missing or cannot be read, `wordcount` exits with code 2, not 1. My scripts treat 2 as an error. Keep the message as it is.”（文件不存在或无法读取时，`wordcount` 以退出码 2 退出，而不是 1。我的脚本把 2 当作错误。提示信息保持不变。）随后 Troy 批准了这次架构变更。

需要权衡的因素：

- Troy 的脚本必须把每一种文件错误都当作错误。
- 标准错误里的那一行 `wordcount: <按原样输入的 FILE>: <原因>` 保持不变。
- 需求只要求文件不存在时退出码不为 0，所以两种退出码都满足需求。
- `argparse` 对命令行写错总是以退出码 2 退出，Python 对未捕获的异常总是以退出码 1 退出。不写额外代码就改不了这两点。

## 3. 决定

1. 对 cli 捕获的每一种文件错误，即 `OSError` 及其子类和 `UnicodeDecodeError`，cli 向标准错误写同样的一行 `wordcount: <按原样输入的 FILE>: <原因>`，并返回退出码 2。这取代 ADR-0001 第 4 点中的“返回 1”。ADR-0001 的其余内容不变。
2. 文件错误和命令行写错共用退出码 2，只有标准错误里的文字能区分它们：文件错误是一行 `wordcount: <按原样输入的 FILE>: <原因>`，命令行写错是用法说明。
3. cli 仍然不捕获其他异常。Python 向标准错误写出 traceback 并以退出码 1 退出，所以退出码 1 只表示缺陷。
4. `wordcount` 的退出码：成功为 0，文件错误或命令行写错为 2，缺陷为 1。

## 4. 考虑过的方案

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 每一种文件错误都用退出码 2，提示信息不变（采用） | Troy 的脚本把每一种文件错误都当作错误。退出码 1 留给缺陷，脚本能区分缺陷和输入有误。不需要新代码：`argparse` 已经用 2。 | 文件错误和命令行写错共用一个退出码，脚本要读标准错误才能区分。F04 原型和 v0.2 测试计划写的是退出码 1，已经过时。 |
| 文件错误保持退出码 1（ADR-0001 原文） | 与原型和 v0.2 测试计划一致。文件错误和命令行写错的退出码不同。 | 违背 Troy 的决定。Troy 的脚本不把 1 当作错误。文件错误和缺陷共用退出码 1。 |
| 文件错误用单独的退出码，例如 3，或每种原因一个退出码 | 每种失败都有自己的退出码。 | Troy 的脚本把 2 当作错误，而不是 3。要说明和测试的退出码更多，而错误那一行已经说明了区别。 |

## 5. 影响

- 运行 `wordcount` 的脚本看到：得到词数时为 0，文件错误或命令行写错时为 2，只有程序出现缺陷时为 1。
- 要区分文件错误和命令行写错，脚本读标准错误。`wordcount: <按原样输入的 FILE>: <原因>` 这一行表示文件错误，以 `usage:` 开头的行表示命令行写错。
- 错误那一行、原因文字和标准输出都不变。需求不变。
- F04 的接口设计从 0.2 版起规定文件错误的退出码为 2。尚未编写的 F04 测试计划要求退出码 2。
- v0.2 测试计划在文件不存在、文件不是有效 UTF-8 和 PowerShell 会话这几个场景里要求退出码 1。在编写 v0.2 的测试之前，要用一个 `[docs]` PR 把它们改成 2。F04 原型仍显示 `$LASTEXITCODE` 为 1；F04 的设计记录了这个差别。
- 一旦 Troy 的脚本依赖退出码 2，再改它就会让这些脚本出错。
