# F05 Line count option: test plan

## 1. Feature

- ID and name: F05 Line count option
- Design: [design.md](design.md)

## 2. Cases

F05 changes two external interfaces, and the cases reach each one the way its caller does.

- **`main`.** F05-T01 to F05-T18 call it in the test's own process, as `from troy_mode_trial.cli import main`. They read standard output and standard error with pytest's `capsys`, and make the test's `tmp_path` the working directory with `monkeypatch.chdir`, unless a case says otherwise. Through `capsys` a line break is `\n` on both systems.
- **`wordcount`.** F05-T19 to F05-T24 start the installed program as a new process, with no shell, its working directory set to `tmp_path`, and standard output and standard error captured as bytes. The test finds the program as F04's cases do: in the scripts folder of the Python that runs the tests, `sysconfig.get_path("scripts")`, with `shutil.which("wordcount", path=...)`. If the program is not there, the test fails. It never skips. In these cases `<NL>` is `os.linesep` as bytes: `\n` on Linux and `\r\n` on Windows.

Each test makes its own files in `tmp_path` and writes them in binary mode, as the exact bytes the case gives. Unless a case says otherwise, `notes.txt` holds `Hello world\n  troy-mode  trial\n`, the design's example, which has 2 lines and 4 words. `windows.txt` holds `Hello world\r\n  troy-mode  trial\r\n`. `latin1.txt` holds `café au lait\n` in Latin-1, so its bytes start `63 61 66 E9 20`. `sub` is an empty folder in `tmp_path`. Characters outside ASCII in a file's content or name are UTF-8. The suite runs on Windows 11 and on Linux. A case expects the same result on both, unless it names a system.

"Exactly" means the whole text: for example, standard error is exactly `wordcount: missing.txt: no such file\n` means that line and nothing else.

**The usage line depends on whether F06's code has landed.** F06 is built at the same time, and design section 2.1, in its landing-order paragraph, gives the usage line for both orders. `<USAGE>` in this plan is:

- `usage: wordcount [--lines] FILE` while F06's code is not on the branch under test, so `--chars` is an unknown option.
- `usage: wordcount [--lines | --chars] FILE` once F06's code is on that branch.

A case that checks a usage line first asks the command which state holds, through the same interface it tests, and throws away the output of that call. A `main` case calls `main(["--chars", "notes.txt"])`: if it returns `0`, F06's code has landed; if it raises `SystemExit` with code `2`, it has not. A `wordcount` case runs `wordcount --chars notes.txt` in the same way: exit code 0 means F06's code has landed, and exit code 2 means it has not. The case then expects the exact line of that state. This keeps every case exact in both landing orders. A fixed line would not work: once F05 is accepted, its tests must pass in every PR (R10), and if F06's code lands second, F06's implementation PR changes the usage line but may not change tests (R08).

"Usage error" means: `main` raises `SystemExit` whose `code` is `2`, or the program exits with code 2, and standard output is empty, and standard error holds exactly two lines, the first exactly `<USAGE>` and the second starting with `wordcount: error: `.

The mock for F05 leaves `main` exactly as it is on main at that time, so the command has no `--lines` option yet. Against it, every case fails because `--lines` is not implemented, and none fails on an import or a build error (R09). The cases need no name that main lacks, and `wordcount` is already installed by F04. Each count case and file-error case gets a usage error instead of its result, because the mock calls `--lines` an unrecognized argument. Each usage-error case gets a first line without `--lines`, `usage: wordcount FILE` or `usage: wordcount [--chars] FILE`, which differs from `<USAGE>`. Each `wordcount` case gets exit code 2 and a usage line instead of its output.

## 3. Performance cases

None. Design 2.1 and 2.2 set no performance target, and requirements 7.1 sets none for the project (R14).

## 4. Not tested

| What | Why |
| --- | --- |
| The count and the errors of `wordcount --chars FILE`. | F06's design defines them, and F06's test plan checks them. F05 uses `--chars` only to find the state of section 2 and to check that it cannot come with `--lines`. |
| `wordcount FILE` without an option, in full. | F04's cases check it, and they must pass in every PR (R10). F05-T18 and F05-T19 check once more that the words are still counted beside `--lines`. |
| The usage lines that F04's and F06's test plans expect. | Design section 3 lists them. F06's test-plan PR changes F04's plan, and F06's own plan is that team's. This plan does not change them. |
| The exact message for `--lines=VALUE`. | The design leaves it to argparse's own words and fixes only that it is a usage error. F05-T14 checks that. |
| A bug: an exception other than a file error reaches the caller, Python writes a traceback, and the program exits with code 1. | No input through `main` or `wordcount` makes counting raise any other exception. Provoking one would need replacing the counting function inside cli, which tests an internal detail, not an external interface. Against the mock, such a test would also pass, which R09 forbids. |
| `PermissionError` for an unreadable file on Windows. | Removing a file's read right on Windows needs access control lists, which a portable test cannot set and reset reliably. F05-T11 checks the same reason on Linux, and F05-T10 checks the Windows `PermissionError` for a folder. |
| That the file is closed before the command exits. | `main` reads the file only through `count_lines`, whose closing F02's cases check. F05-T18 checks that the command writes no file. |
| That output uses `write` and not `print()`. | Both give the same text, so a caller cannot tell them apart. ruff's T20 rule enforces it (architecture section 8). |
| Items of `argv` that are not `str`, and a path that holds the character U+0000. | Design 2.2 allows only `str` items, so other types are outside the contract. No shell can pass U+0000 in an argument, so `wordcount` never receives one. |
| The bytes of a file name outside ASCII on standard error when `wordcount` writes to a pipe on Windows. | Python then encodes standard error in the system's code page, so the bytes depend on the machine. F05-T08 checks the text of such a message through `main`, and F05-T24 checks that such a name reaches the program and is counted. |
| PowerShell finding `wordcount`, `$LASTEXITCODE`, quotes as PowerShell removes them, and the need to install the project again once F05 lands. | CI runs on Linux, without PowerShell. The v0.3 version test plan runs the command in Windows PowerShell on Troy's PC. F05-T24 checks that a quoted argument reaches the program as one argument. |
| Performance. | No performance target exists (R14). |

## 5. Alignment with the Interface Designer

None. The design answered every question this plan raised. Its landing-order paragraph gives the usage line and the meaning of `--chars` for both orders, so section 2 checks the line of whichever state the branch is in. The Architect's note in design section 4 asked that whichever of F05 and F06 lands its test PR second update the expected usage line. For F04's cases, F06's test-plan PR now checks only the start of the usage line, so no F05 PR changes them. For F05's own cases, the state check of section 2 gives the right line in both orders, so no later PR needs to change them.
