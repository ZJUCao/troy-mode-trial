# F06 Character count option: test plan

## 1. Feature

- ID and name: F06 Character count option
- Design: [design.md](design.md)

## 2. Cases

F06 has three external interfaces, and the cases reach each one the way its caller does.

- **`count_chars`.** F06-T01 to F06-T17 import it as a caller does, `from troy_mode_trial import count_chars`.
- **`main`.** F06-T18 to F06-T31 call it in the test's own process, as `from troy_mode_trial.cli import main`. They read standard output and standard error with pytest's `capsys`, and make the test's `tmp_path` the working directory with `monkeypatch.chdir`, unless a case says otherwise. Through `capsys` a line break is `\n` on both systems.
- **`wordcount`.** F06-T32 to F06-T35 start the installed program as a new process, as F04's plan does: no shell, the working directory set to `tmp_path`, standard output and standard error captured as bytes, and the program found with `shutil.which("wordcount", path=sysconfig.get_path("scripts"))`. If the program is not there, the test fails. It never skips. In these cases `<NL>` is `os.linesep` as bytes.

Each test makes its own files in `tmp_path` and writes them in binary mode, as the exact bytes the case gives, so that `\r\n` reaches the program as two characters and Windows never turns `\n` into `\r\n`. In the inputs, `\xXX`, `\uXXXX`, and `\UXXXXXXXX` name one Unicode code point, which the test encodes as UTF-8, and `EF BB BF` names the bytes of a byte order mark. Unless a case says otherwise, these files have this content:

- `notes.txt` holds `Hello world\n  troy-mode  trial\n`, the design's example: 31 characters and 4 words.
- `windows.txt` holds `EF BB BF` followed by `Hello world\r\n  troy-mode  trial\r\n`, as Notepad saves it: 33 characters.
- `hello.txt` holds `你好\r\n`: 8 bytes and 4 characters.
- `latin1.txt` holds `café au lait\n` in Latin-1, so its bytes start `63 61 66 E9 20`.
- `sub` is an empty folder.

Characters outside ASCII in a file's name are UTF-8. The suite runs on Windows 11 and on Linux. A case expects the same result on both, unless it names a system.

"Exactly" means the whole text, as in F04's plan. "Usage error" means: `main` raises `SystemExit` whose `code` is `2`, or the program exits with code 2, and standard output is empty, and standard error holds exactly two lines, the first starting with `usage: wordcount ` and holding `--chars`, and the second starting with `wordcount: error: `. The text `--chars` in the usage line is what tells F06's usage line from F04's, so every usage error case fails against the mock. It stays true once F05 adds `--lines`.

"The F06 usage line" means a whole line that matches the regular expression `^usage: wordcount \[[^\]]*--chars[^\]]*\] FILE$`: it starts with `usage: wordcount `, holds `--chars` inside one pair of square brackets, and ends with ` FILE`. Design section 2.1's line `usage: wordcount [--chars] FILE` matches it, and so does `usage: wordcount [--lines | --chars] FILE`. F04's line `usage: wordcount FILE` does not. Only F06-T28 and F06-T34 check the full usage line, against this pattern. No test of an accepted feature fails in any PR of F06, because F04's plan 1.1 no longer fixes the full usage line: F04-T11, F04-T12, F04-T13, and F04-T21 check only that it starts with `usage: wordcount `, with exit code 2, empty standard output, and the error line. They pass before and after F06's code.

F05 is built at the same time. Its design (PR #67, approved by the Architect) makes the usage line `usage: wordcount [--lines | --chars] FILE` once both features land, and design section 3 says that whichever of F05 and F06 lands second keeps the option of the other. F06-T28 and F06-T34 pass with either line, so they do not depend on which feature lands first, and no F06 case changes when F05 lands. They still fail against the mock, whose usage line is F04's (R09).

Against the mock, every case fails because the option is not implemented. This assumes that the mock PR adds `count_chars` with a body that raises `NotImplementedError`, exports it from `troy_mode_trial`, and leaves `main` and its usage line as F04 built them. Then each `count_chars` case gets `NotImplementedError` instead of its result or its exception. Each `main` case gets a usage error that does not know `--chars`, or a usage line `usage: wordcount FILE` instead of the new one. Each `wordcount` case gets exit code 2 and that usage error instead of its output (R09). If the mock already accepts `--chars` and shows the new usage line, the usage error cases would pass against it, which R09 does not accept, so the Test Engineer reports it before the test PR.

## 3. Performance cases

None. Design sections 2.1, 2.2, and 2.3 set no performance target, and requirements 7.1 sets none for the project (R14).

## 4. Not tested

| What | Why |
| --- | --- |
| `wordcount FILE` and `main` without `--chars`: the word count, its error lines, and its usage errors other than the usage line. | F04-T01 to F04-T22 check them. F04's plan 1.1 loosens only its usage error cases, which now check that the usage line starts with `usage: wordcount `. A new F06 case for them would pass against the mock, which R09 forbids. F06-T20 and F06-T32 still check one word count next to a character count. |
| A bug: an exception other than a file error reaches the caller, Python writes a traceback, and the program exits with code 1. | As in F04's plan: no input through an external interface makes counting raise any other exception, and provoking one would need replacing a function inside cli. |
| The text of an exception's message from `count_chars`, such as `[Errno 2] No such file or directory: 'missing.txt'` in the design's example. | Python writes the message, and the design promises only the exception type (requirements Q4). F06-T10 to F06-T14 check the type. |
| `PermissionError` for an unreadable file on Windows. | Removing a file's read right on Windows needs access control lists, which a portable test cannot set and reset reliably. F06-T12 and F06-T26 check the same behavior on Linux. |
| Which of `IsADirectoryError` and `PermissionError` Windows raises for a folder. | The design allows either on Windows. F06-T11 accepts either there and asks for `IsADirectoryError` on Linux. |
| The usage line word for word, and the message for `--lines` with `--chars` once F05 adds `--lines`. | F05's design fixes the usage line once both features land, and that message (design section 3). F06-T28 and F06-T34 check the usage line against a pattern that both lines match, and F06-T29 checks only that `--lines` with `--chars` is a usage error. |
| Items of `argv` that are not `str`. | Design section 2.2 allows only `str` items, so other types are outside the contract. |
| The bytes of a file name outside ASCII on standard error when `wordcount` writes to a pipe on Windows. | As in F04's plan: Python then encodes standard error in the system's code page, so the bytes depend on the machine. F06-T35 checks that such a name reaches the program and is counted. |
| PowerShell finding `wordcount`, `$LASTEXITCODE`, quotes as PowerShell removes them, and the need to install the project again once F06 lands. | CI runs on Linux, without PowerShell. The v0.3 version test plan runs the command in Windows PowerShell on Troy's PC. F06-T35 checks that a quoted argument reaches the program as one argument. |
| Performance. | No performance target exists (R14). |

## 5. Alignment with the Interface Designer

None. The design answered every case question this plan raised. The Architect's notes in design section 4 asked the Test Manager to change only the expected first line of F04-T11, F04-T12, F04-T13, and F04-T21, and to write each file in binary mode so that `\r\n` reaches `count_chars` as two characters. Section 2 of this plan asks for the second. For the first, F04's plan 1.1 loosens that line to its start, `usage: wordcount `, instead of fixing it as `usage: wordcount [--chars] FILE` as design section 3 says. The Product Manager asked for this in round 2: a test of an accepted feature must pass in every PR (R10), so an F04 test that expects F06's usage line would fail in F06's test PR. F06-T28 and F06-T34 check the full usage line instead. In round 3 the Product Manager asked that they not depend on whether F05 or F06 lands first, so they check the usage line against a pattern that holds both before and after F05 lands. The design's interfaces do not change.
